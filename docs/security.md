# Security

Backups are what you fall back on after an attack, so the backup system must survive the
attack too. This page explains what restic-fleet protects against, what it doesn't, and which
choices are yours.

## The short version

- Backups are **encrypted on the machine** (restic: AES-256 + Poly1305) before they are sent.
  The backup server stores ciphertext.
- The server is **append-only**. A hacked machine, or ransomware on it, can't delete or overwrite
  its old backups.
- Repositories are **private**. Each machine can only reach its own.
- Every connection is **TLS**, and machines trust only your fleet's CA.
- All secrets are **generated by restic-fleet**, stored with tight permissions, and never put on a
  command line or in logs.
- The **controller** (your `credentials/` folder) is the crown jewel. Protect it.

## What each part can do if compromised

| If an attacker controls… | …they can | …but they cannot |
|---|---|---|
| **a machine** | read that machine's backups; add new snapshots; fill its repository with junk | delete or rewrite its existing snapshots (append-only); see or touch other machines' repositories (private repos + per-machine login) |
| **the backup server** | delete or corrupt any repository; with maintenance **on**, read all backups | with maintenance **off**, read any backup (it never has the repository passwords) |
| **the dashboard** (its process) | read status data; send fake alerts; show a fake status | read or change any repository (it runs as its own user and has no repository credentials); learn machine tokens (it stores only their SHA-256 hashes) |
| **a dashboard login** | see status, sizes, job names, error messages | change anything: the dashboard is read-only |
| **the controller / `credentials/`** | everything | — |

Two conclusions follow:

1. **Harden the backup server as your most important server.** Allow SSH by key only, give only
   a few people access, and keep it off the networks your machines share with the internet if you
   can.
2. **A single backup server is a single copy.** Against a server compromise, fire or a provider
   outage, keep an [off-site copy](operations.md#off-site-copy) the server can't delete.

## The maintenance trade-off

Retention and pruning *delete* data, so they can't run through the append-only server. Someone
with the repository password has to run them somewhere. restic-fleet gives you the choice:

**`fleet_server_maintenance: true` (default).** The backup server keeps each repository's password
(`/etc/restic-fleet/repos/<machine>.pass`, `root:restic`, `0640`) and prunes and checks locally
once a week.

- ✅ Retention happens automatically, and weekly integrity checks read real data.
- ⚠️ Whoever owns the backup server can decrypt the backups.

**`fleet_server_maintenance: false`.** The server never sees a repository password.

- ✅ A compromised backup server can destroy backups, but can't read them.
- ⚠️ Nothing is pruned automatically, and repositories only grow. You run maintenance yourself from a
  trusted machine:

  ```bash
  # on the backup server, supplying the password only for this run
  restic -r /srv/restic-fleet/web1 --password-command "ssh admin@vault cat web1.pass" \
    forget --prune --keep-daily 7 --keep-weekly 4 --keep-monthly 6 --group-by host,paths,tags
  restic -r /srv/restic-fleet/web1 --password-command "…" check --read-data-subset 5%
  ```

Choose **true** when you trust the backup server at least as much as the machines, which is the
usual case for a team running its own servers. Choose **false** when the backup server is hosted
somewhere less trusted than the data (a cheap storage VPS, a third party).

## Secrets

All generated on the controller on the first deploy (48 random letters and digits each), and reused afterwards:

| Secret | Controller | Where it's deployed | Used for |
|---|---|---|---|
| repository password | `credentials/repo-password/<m>` | machine `/etc/restic-fleet/repo.pass` (0600 root); server `repos/<m>.pass` (only with maintenance on) | encrypting the backups |
| rest-server password | `credentials/rest-password/<m>` | machine `fleet.env` (0600 root); server `rest-server.htpasswd` (**bcrypt hash**) | logging in to rest-server |
| report token | `credentials/report-token/<m>` | machine `report.header` (0600 root); dashboard config (**SHA-256 hash**) | reporting to the dashboard |
| server report token | `credentials/server-report-token` | server only | maintenance and stats reports |
| metrics token | `credentials/metrics-token` | dashboard config (**SHA-256 hash**) | `/metrics` |
| dashboard admin password | `credentials/dashboard-admin-password` | dashboard `users.json` (**scrypt hash**) | signing in |

How they are handled:

- Secrets are passed to programs **on stdin or in files, never as arguments**, so they don't show
  in `ps` or shell history.
- Ansible tasks that touch secrets use `no_log: true`, so they don't appear in deploy output or in CI.
- Removing a machine from the inventory removes its rest-server login, its dashboard token and
  (with maintenance on) its repository password from the server.
- To rotate secrets, see [Operations → Rotating secrets](operations.md#rotating-secrets).

## Network and TLS

- A private CA (ECDSA P-256, 10 years) is created on the backup server. The server certificate
  (825 days) names exactly the configured server address, and it's renewed automatically on
  deploy when fewer than 30 days remain or the address changes.
- Machines connect with `RESTIC_CACERT`, and `curl --cacert` for reports. **They trust your CA
  only**, not the public CA bundle, so a certificate issued elsewhere for the same name is refused.
- TLS 1.2 is the minimum for rest-server and the dashboard.
- If `ufw` is active, rest-server (:8000) is reachable only from the machines. restic-fleet never
  enables a firewall or changes existing rules, so it can't lock you out.

## The dashboard

- A Python standard-library server. No web framework, no npm packages, and nothing loaded from
  other sites.
- **Sign-in:** scrypt password hashes; 10 failed attempts per address in 15 minutes locks that
  address out; the same error message for a wrong user and a wrong password.
- **Sessions:** HMAC-signed, 12 hours, in a `__Host-` cookie that is `HttpOnly`, `Secure` and
  `SameSite=Strict`.
- **Forms:** every POST must come from the same origin (checked against `Origin`/`Referer`), which
  blocks cross-site request forgery.
- **Headers:**
  - a strict `Content-Security-Policy` (`default-src 'none'`; scripts and styles only from the
    dashboard itself; no inline code);
  - `Strict-Transport-Security`;
  - `X-Frame-Options: DENY`;
  - `Referrer-Policy: same-origin`;
  - `X-Content-Type-Options: nosniff`.
- **Rendering:** the page is built with DOM methods and `textContent` only, never HTML strings, so
  a hostile error message or job name can't inject markup.
- **Report API:** bearer tokens compared in constant time; strict validation of every field; body
  size limits.

## Services and sandboxing

Every long-running service runs under systemd with a dedicated user and sandboxing:

| Service | User | Highlights |
|---|---|---|
| `restic-fleet-rest-server` | `restic` | writes only to `fleet_data_dir`; `ProtectSystem=strict`, `NoNewPrivileges`, no capabilities |
| `restic-fleet-dashboard` | `rfdash` | writes only to its state dir; no capabilities; `MemoryDenyWriteExecute`; syscall filter; `UMask=0077` |
| `restic-fleet-collect` / `-maintain` | `restic` | writes only to the repositories and its cache; `ProtectSystem=strict`, no capabilities, private `/tmp` |
| `restic-fleet-backup` (machines) | root (must read everything it backs up) | low CPU/IO priority; runs once and exits |

## Supply chain

- restic and rest-server are downloaded from their official GitHub releases, **pinned to a version,
  and verified against SHA-256 checksums in this repository** before being installed. A tampered
  download fails the deploy.
- The Ansible roles use only `ansible.builtin` modules, with no third-party collections.
- The dashboard and server scripts use only the Python standard library.
- The controller installs `ansible-core` from PyPI into a local virtualenv, within a version range.

## Checklist for production

- [ ] `credentials/` backed up somewhere safe and **not** in a public repository
- [ ] Backup server: SSH keys only, few admins, automatic security updates
- [ ] Firewall on the backup server: 8000 and 8443 only from where they're needed
      (`fleet_dashboard_allow_from`)
- [ ] Chose `fleet_server_maintenance` deliberately
- [ ] An off-site copy of the repositories that the backup server can't delete
- [ ] Alerts set up, and tested by stopping a machine's timer until it goes overdue
- [ ] A restore tested this month
